# 复杂层级中的 Diátaxis

## 文档内容的结构

对大多数文档而言，套用 Diátaxis 相当直接。界定关注领域的产品边界清晰，完全可以整理出一种文档编排，例如：

``` text
首页                      <- 着陆页
    教程                  <- 着陆页
        第一部分
        第二部分
        第三部分
    操作指南              <- 着陆页
        安装
        部署
        扩容
    参考                  <- 着陆页
        命令行工具
        可用端点
        API
    阐释                  <- 着陆页
        最佳实践建议
        安全概览
        性能
```

每一种情形下，着陆页都会概述其下内容。例如教程的着陆页会说明教程提供什么，为其提供语境。

### 再加一层级

即便非常大的文档集也可以这样用；只是再过一阵子，各节内部或许值得再做分组。可以通过增加一层层级来实现——例如把不同的安装方式分开写：

``` text
首页                      <- 着陆页
    教程                  <- 着陆页
        第一部分
        第二部分
        第三部分
    操作指南              <- 着陆页
        安装                <- 着陆页
            本地安装
            Docker
            虚拟机
            Linux 容器
        部署
        扩容
    参考                  <- 着陆页
        命令行工具
        可用端点
        API
    阐释                  <- 着陆页
        最佳实践建议
        安全概览
        性能
```

## 目录页

目录页——通常是首页以及各着陆页——概览其涵盖的材料。

做好一张目录页需要技巧；给读者的体验值得认真琢磨。

### 列表过长的问题

没有内在机械顺序（数字或字母）的列表，一旦超过少数几项，人就很难读。*一般认为大约七条还算是舒适的极限。*若目录里经常出现更长的列表，恐怕就得想办法拆成更小的列表。

一如既往，最重要的是**读者的体验**。Diátaxis 之所以有效，是因为它贴合用户需求——若你落实 Diátaxis 的方式显得别扭或难看，就需要换一种用法。

### 概览与导语

**着陆页本身的正文应当读起来像一篇概览。**

也就是说，不要只罗列其他内容的清单，而要去介绍它们。*永远记住：你写作的对象是活生生的读者，而不是在填一张分类表的格子。*

标题与导语片段能抓住目光、提供语境；例如一张**操作指南的着陆页**可以是这样：

``` text
操作指南
========

Lorem ipsum dolor sit amet, consectetur adipiscing elit.

安装类指南
----------

Pellentesque malesuada, ipsum ac mollis pellentesque, risus 
nunc ornare odio, et imperdiet dui mi et dui. Phasellus vel 
porta turpis. In feugiat ultricies ipsum.

* 本地安装       |
* Docker         |  链向
* 虚拟机         |  各篇指南
* Linux 容器     |

部署与扩容
----------

Morbi sed scelerisque ligula. In dictum lacus quis felis 
facilisisvulputate. Quisque lacinia condimentum ipsum 
laoreet tempus.

* 部署实例       |  链向
* 为应用扩容     |  各篇指南
```

## 二维问题

更棘手的是：当 Diátaxis 勾勒出的结构撞上另一套结构时——常见的是文档里按主题划分的结构，或文档要同时服务差异极大的用户类型。

例如，某产品在陆、海、空场景下使用，虽是同一产品，用法却相当不同；在陆上使用的用户，很可能永远不会在海上使用。

又或者，产品文档要兼顾：

- 最终用户；
- 在其上搭建其他产品的开发者；
- 参与维护的贡献者。

仍是同一产品，关切却大相径庭。

再举一例：同一产品可部署在不同公有云上，而每家云的工作流、命令、API、图形界面、约束等都大不相同。尽管仍是同一产品，对各路用户而言，需要知晓与执行的内容非常不同——他们需要的已不是面向抽象「产品」的文档，而是面向

- *某公有云甲上的产品*
- *某公有云乙上的产品*
- 等等……

于是，我们*可以*选定这样一种总体结构：

``` text
教程
    面向陆上用户
        [...]
    面向海上用户
        [...]
    面向空中用户
        [...]
[随后同样拆分操作指南、参考与阐释]
```

也可以改用这一种：

``` text
面向陆上用户
    教程
        [...]
    操作指南
        [...]
    参考
        [...]
    阐释
        [...]
面向海上用户
    [教程、操作指南、参考、阐释各节]
面向空中用户
    [教程、操作指南、参考、阐释各节]
```

哪一种更好？两种似乎都有大量重复。那陆、海、空之间可共享的材料又怎么办？

### 问题*究竟*是什么？

首先，这绝不只是 Diátaxis 特有的难题——无论如何管理文档都会困难。不过 Diátaxis 像在许多别的问题上一样，有助于把问题暴露出来：它让问题显影，并迫使我们正视。

其次，这类问题也点出一种常见误解。Diátaxis 不是把文档硬塞进格子的四格方案。它提出四种不同性质的文档，并围绕它们来组织内容，但这并不意味着层级里必须刚好有四个分区、各对应一类。

## 把 Diátaxis 当作一种方法

Diátaxis 可以用一张图漂亮地概括——但它*并不等同于*那张图。

应把它理解成一种与文档相处的方式：识别四种不同需求，并依此写作与组织材料。

这样做*往往*会走向清晰、显式、按四类划分的结构——但那是良好实践里常见的结果，而不是唯一终点。

## 用户优先的考量

**Diátaxis 的底层是对用户需求的关注**，我们仍应让这一关切来指引方向。

要书写的是产品*在读者手中与心中*的样子。（可惜对许多产品作者来说，他们如何设想产品，往往没那么要紧。）

若陆、海、空场景下的产品，实质上像是三款不同的产品、面向三类不同的用户？

那就从这里出发来思考。

若文档要同时满足用户、开发者与贡献者，*他们*眼中的产品各是什么？是否应假设：把产品嵌入其他作品的开发者，通常也需要理解典型用法；而贡献者是否也需要具备开发者所知？

那样一来，某些部分（例如教程）或许可以更松散地安排：让面向开发者的内容接在用户内容之后，却把贡献者的操作指南与用户、开发者完全分开。

凡此种种。若最终结构并不是 [我们一开始那种简单、毫无波折的安排](../getting-started/start-here.md)，也无妨——只要仍按 Diátaxis 原则做了有条理的区分，没有把不同形式与目的搅在一起。

### 该复杂时就允许复杂

文档应当复杂到「必须如此」的程度；有时结构自然会变得复杂。

但只要逻辑清楚，并采用贴合读者需求的模式，再复杂的结构也可以做得易于航行。
