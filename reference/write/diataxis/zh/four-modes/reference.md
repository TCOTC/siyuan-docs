# 参考手册

**参考手册是对「机器」及其操作方式的**技术描述**。参考材料以**提供信息**为导向。**

------------------------------------------------------------------------

参考材料包含用户在工作中查阅的*命题式或理论性*知识。

参考指南的唯一目的，是在尽可能简洁、又有条理的前提下进行**描述**。教程与操作指南的内容由用户需求牵引，而参考材料则由它所描述的产品牵引。

<img src="https://diataxis.fr/images/overview-reference.png" class="sidebar"
alt="参考——面向信息、理论性知识，服务于我们的工作" />

在软件领域，参考手册描述软件本身——API、类、函数等——以及如何使用它们。

用户需要参考材料，因为他们需要**真相与确定性**——在工作中能站稳脚的坚实平台。良好的技术参考对赋予用户开展工作的信心至关重要。

------------------------------------------------------------------------

## 参考即描述

参考材料描述「机器」。它应当是**冷峻的**。人几乎不是*读*参考，而是*查*参考。

参考中不应有疑虑或歧义；它必须**完全权威**。

参考材料像地图。地图告诉你关于地域你需要知道什么，而不必亲自跑遍地域去核对；参考指南对产品及其内部机制起同样作用。

尽管参考不应试图展示如何完成任务，它却常常需要包含某物如何运作或如何正确使用的描述。

<div class="sidebar">

不幸的是，太多软件开发者以为自动生成的参考就是所需的全部文档。

</div>

部分参考材料（如 API 文档）可由所描述的软件自动生成，这是保证其与代码保持忠实一致的有力方式。

------------------------------------------------------------------------

## 关键原则

### 只描述，且仅描述

*中性描述*是技术参考的首要律令。

<div class="sidebar">

**风格与形式**

- 冷峻、不妥协
- 中立、客观、事实性
- 按机器自身的结构来组织

</div>

最难的事情之一，是**中性**地描述某物。那不是自然的沟通方式。自然的是解释、指导、讨论、发表意见——这些都与参考的需求相悖，后者要求准确、精确、完整与清晰。

人们很容易忍不住加入指导与解释，只因为描述似乎太单薄、不够用，而我们确实也需要别的东西。应改为**链接到**操作指南、阐释与入门教程。

### 采用标准版式

**参考材料在一致时最有用。** 标准版式让我们能有效使用参考。你的任务是把用户需要知道的东西放在他们预期能找到的位置，用他们熟悉的格式呈现。

写作中尽可以炫词汇、玩多风格以取悦读者，但参考材料**绝不**是干这个的地方。

### 尊重机器的结构

地图与它所代表的地域之间的对应关系，帮助我们用前者穿行后者。文档也应如此：**文档结构应镜像产品结构**，使用户能同时在两者中推进。

这并不意味着把文档硬塞进不自然的结构。重要的是，代码中的逻辑、概念安排与关系应有助于理解文档。

### 提供示例

**示例**是提供说明、帮助读者理解参考的有价值方式，同时又不至于偏离「描述」的本职。例如，一条命令的用法示例可以简洁地说明它及其语境，而不掉进试图解释或指导的陷阱。

## 饮食与烹饪的类比

你可能会查看食品包装上的信息，以帮助决定该怎么做。

当你寻找信息——相关事实——时，你不希望被观点、臆测、指令或诠释打扰。

<img src="https://diataxis.fr/images/lasagne.jpg" class="floated"
alt="千层面包装背面的信息" />

你也期望信息以标准方式呈现，这样当你需要了解营养、储存方式、配料、健康影响等时，能快速找到并确信可靠。

于是你会期待看到例如：*可能含有小麦成分*。或：*净重：1000g*。

你绝不会希望把菜谱或营销话术与这类信息混在一起；那可能**字面意义上**带来危险。

食品上参考信息的呈现方式如此重要，通常受法律规制；所有参考文档都应抱持同样严肃的态度。
