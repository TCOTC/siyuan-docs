# 操作指南

**操作指南是**指引**读者穿过问题或走向结果的说明。操作指南以**达成目标**为导向。**

------------------------------------------------------------------------

操作指南帮助用户**正确、安全**地完成某件事；它引导用户的*行动*。

它关心的是*工作*——在真实世界的问题场域中从一侧导航到另一侧。

<img src="https://diataxis.fr/images/overview-how-to.png" class="sidebar"
alt="操作指南——面向任务、实际步骤，服务于我们的工作" />

例子可以是：*如何校准雷达阵列*；*如何在 pytest 中使用 fixture*；*如何配置重连退避策略*。反过来，*如何构建一个 Web 应用*则不是——那没有对准具体目标或问题，而是一个极其开放的技能领域。

操作指南重要，不仅因为用户需要把事情做成：文档里操作指南的列表也在**框定你的产品究竟能做什么**。丰富的操作指南列表令人鼓舞地暗示产品的能力。

写得好、又对准真问题的操作指南，往往会成为文档中**阅读量最大**的部分。

------------------------------------------------------------------------

## 操作指南对准的是问题

**操作指南必须从用户视角撰写，而不是从「机器」视角。** 操作指南代表某人**要完成的事**。换言之，它由**用户需求**定义。每一篇操作指南都应回应一个**人的项目**：人用手头的工具需要做什么才能得到所需结果。

这与常见的操作指南写法形成强烈对比——那种写法往往按工具或系统能执行的**操作**来定义指南。后者的毛病是对用户价值小；它不对准用户的任何需求，而是对准工具、对准让机器走完一套动作。

这根本上是*意义*的差别。意义来自目的与需求。机器的功能性里没有目的或需求，只是一串因果、输入与输出。

考虑：

- 「要关水流，顺时针拧水龙头。」
- 「要部署目标数据库配置，选择合适选项后按 **部署**。」

<div class="sidebar">

我们确实不需要被告知用电源键开机，但令人震惊的是，软件文档里的操作指南常常就写到这个层次。

</div>

上面的例子*看起来*像指导范例，其实**不是**。

它们多半是任何具备基本能力——在该领域工作的人——就该知道的**无用信息**。标准化界面与普遍预期知识，应已让人明白多数动作的效果。

其次，它们与**目的**脱节。用户真正可能需要的是：

- 为某个目的该放多少水、多猛的水流
- 哪些数据库配置选项对应哪些真实世界需求

<div class="sidebar">

操作指南讲的是目标、项目与问题，不是工具。

</div>

工具在操作指南里只是**配角**，是达成用户目的的手段。当然，有时某一目的与某一工具或系统部件紧密对齐，你就会看到操作指南集中写那一块。同样常见的是，一篇操作指南会横跨不同工具或子系统，按**人需要完成的事**把一系列活动串起来。无论哪种情况，**是那个项目**定义操作指南必须覆盖什么。

------------------------------------------------------------------------

## 操作指南不是什么

**操作指南与教程完全不是一回事**。二者常被混淆，但它们服务的用户需求颇为不同。把二者混为一谈，是许多文档困境的根源。关于这一区分，请参阅 [教程与操作指南](https://diataxis.fr/tutorials-how-to/) 的讨论。

另一种混淆是把操作指南仅仅看成**程序性**说明。但解决问题或完成任务并不总能化约为线性程序。真实世界的问题并不总提供线性解法。操作指南里的行动序列有时需要分叉、交叠，有多个入口与出口。操作指南常常需要用户凭借自己的判断来运用它能提供的指引。

------------------------------------------------------------------------

## 关键原则

操作指南关心的是工作——一项任务或问题，带有实践目标。*始终把焦点放在该目标上*。

<div class="sidebar">

**操作指南的特征**

- 对准任务或问题
- 假定用户知道自己想达成什么
- 只有行动，还是行动
- 不跑题、不解释、不教学

</div>

任何额外内容都会分散你与用户的注意力，稀释指南的效力。典型诱惑是**解释**，或为求「完整」而塞进**参考**。二者都不属于引导用户工作。它们妨碍行动；若确实重要，请**链接**出去。

操作指南服务的是**已经胜任**的用户——你可以假定他们知道自己要做什么，并能正确执行你的指示。

### 对准真实世界的复杂

**操作指南需要能适应真实用例。** 若除了你写的那条**极窄**路径外毫无用处，就很少有价值。你不可能覆盖所有情况，因此要以某种方式对可能性保持开放，让用户能把你的指导适配到自己的需求。

### 省略非必要内容

在操作指南里，**实用比完整更有帮助。** 教程需要完整、端到端，操作指南则不必。它应在某种合理、有意义的地方开始与结束，并要求读者自行衔接到自己的工作。

### 提供一套指令

操作指南描述对真实问题或任务的*可执行解法*。形式像契约：若你面临这种局面，可按本方法概述的步骤走过去。步骤的形式是*行动*。

此处的「行动」包括身体动作，也包括思考与判断——解决问题需要想通。操作指南既要写用户**如何做**，也要写用户**如何想**。

### 描述合乎逻辑的序列

操作指南的基本结构是*序列*。它隐含时间上的逻辑顺序，意味着这一顺序有某种意义与道理。

许多情况下，顺序由事物必然性强加（例如第二步依赖第一步完成）。这时方向顺序显而易见。

有时需求更微妙——两个操作或许**先做哪个都行**，但若某一操作能以某种方式帮用户准备好环境或思维，使另一操作受益，这就是把它放在前面的好理由。

### 追求流畅

始终努力把序列扎根于**用户**的活动与思维模式，使指南获得*流畅*：顺滑推进。

达成流畅意味着真正理解用户。在排序上关注意味与道理，需要关注人的思考与行动方式，以及跟指令者当下的需求。

这有时很明显：若工作流让用户在上下文与工具之间反复横跳，显然笨拙低效。但你应看得更深：你在要求用户想什么？他们的思考如何在工作过程中从主题流向主题？你要用户把念头悬置多久才能落实为行动？若你让用户跳回早先的关切，这是必须的还是可避免的？

操作指南关心的不仅是时间上的逻辑顺序，还有**时间中展开的行动**。行动及其指南有节奏与韵律。节奏判断失误或韵律被打断，都会损害流畅。

操作指南写得最好时，会给用户**流动感**。你会遇到一种体验：指南似乎*预判*了你——就像助手把你正要伸手的工具递到你掌心。

### 重视命名

**标题要准确说出这篇操作指南展示什么。**

- 好：*如何集成应用性能监控*
- 差：*集成应用性能监控*（也许文档讲的是该不该集成，而不是怎么做）
- 很差：*应用性能监控*（也许讲*如何*——但也可能是*是否*，甚至只是解释*是什么*）

搜索引擎和人类一样喜欢好标题。

------------------------------------------------------------------------

## 操作指南的语言风格

*本指南演示如何……*  
清楚说明指南帮用户解决的**问题或任务**。

*若你想要 x，就做 y。若要达成 w，就做 z。*  
使用条件式祈使句。

*关于 x 的完整选项列表，请参阅 x 参考手册。*  
不要把与 x 相关的所有可能操作都塞进实用的操作指南里。

------------------------------------------------------------------------

## 饮食与烹饪的类比

把菜谱想成操作指南的绝佳模型。菜谱清楚定义跟做后会得到什么，并**对准具体问题**（*我怎么做……？* 或 *我用……能做什么？*）。

![一份菜谱包含配料表与步骤列表。](https://diataxis.fr/images/old-recipe.jpg)

菜谱的责任**不是**「教」你怎么做。专业厨师即便做过同一道菜许多遍，仍可能照菜谱做——哪怕菜谱就是他自己写的——以确保做得正确。

即便照菜谱做，**也至少需要基本厨艺**。从未下过厨的人不该指望单靠菜谱就能成功，因此菜谱不能替代烹饪课。

期待拿到菜谱的人若得到的是烹饪课，会失望又恼火。同理，当你正忙着把菜做出来时，最不想读的是某道菜的历史背景；好菜谱遵循成熟版式，**排除教学与讨论**，只聚焦**如何**做出眼前这道菜。
