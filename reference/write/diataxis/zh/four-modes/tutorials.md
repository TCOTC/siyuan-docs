# 教程

**教程是在导师指导下发生的**体验**。教程始终以**促进学习**为导向。**

------------------------------------------------------------------------

教程是一种*实践活动*，学习者在其中通过做一件有意义的事、朝某个可达成的目标学习。

教程服务于用户对技能与知识的*习得*——他们的**学习**。它的目的不是帮用户「把事办完」，而是帮他们**学会**。

<img src="https://diataxis.fr/images/overview-tutorials.png" class="sidebar"
alt="教程——面向学习、描述实际步骤的指南，旨在服务我们的研习" />

换言之，教程就是**课**。

要理解：学生会通过动手而学习，但他们*做*的，未必就是他们*学到*的。通过动手，他们会获得理论知识（即事实）、理解、熟悉感。他们会了解事物如何关联与互动，以及如何与事物互动。他们会学到名称、工具、工作流、概念、命令等。诸如此类。

------------------------------------------------------------------------

## 教程即课程

课程意味着教师与学生之间的关系。在这类学习中，*学习发生在学生于教师指导下投入任务之时*。

课程是一种*学习体验*。在学习体验中，重要的是学习者**做了什么**、**发生了什么**；相比之下，教师的讲解与事实陈述远不那么重要。

好课通过向学习者展示他们能在某项技能或某个产品上取得成功，来建立其信心。

### 教师的义务

<div class="sidebar">

当老师并不容易。

</div>

课程是师生之间的一种契约，其中**几乎全部责任**落在教师身上。教师要负责学生学什么、学生为学习要做什么、以及学生的成功。与此同时，学生在这份契约里唯一的责任是专心并尽可能严格遵循教师的指示。学生没有「必须学会、理解或记住」的责任。

同时，你让学生做的练习必须：

- *有意义*——学生要有成就感
- *能成功*——学生必须能完成
- *合乎逻辑*——学生走过的路径要讲得通
- *在有用意义上完整*——学生必须接触到他们需熟悉的一切动作、概念与工具

### 教程的难题

总体而言，教程很少被做好，一部分因为确实难做，一部分因为人们对它理解不足。在软件领域，许多产品缺少好教程，或完全没有教程；教程又常与操作指南混为一谈。

理想课堂里，教师在场，与学生互动，纠正错误并检查学习。在文档里，这一切都不可能。

<div class="sidebar">

撰写与维护教程会消耗惊人的人力与时间。

</div>

要凑齐符合上述全部标准的学习体验已经很难；在许多语境下产品本身快速演进，意味着所有工作要重做一遍，才能保证教程仍履行其职能。

你还会发现，文档里没有哪一部分像教程那样频繁被整体修订。在别处，改动与改进往往可以**离散**进行；在教程里，端到端的学习旅程必须讲得通，改动常常**级联**贯穿整个故事。

最后，教程还有一层额外困难：*要学的是什么*与*要做的是什么*之间的区分。教程作者不仅要清楚用户何时该学会什么，还要设计出一条有意义的**学习旅程**，把这一切都交付出去。

## 关键原则

教程是一个教育学问题。

它不容易，但也不是谜。下文原则——重复、行动、小步、尽早且频繁出结果、具体性等——并非秘密，却并非总被理解。

不过，在实践中应对教育学难题，仍有直接而有效的办法。

<div class="sidebar">

**反教育学诱惑**

- 抽象、概括
- 解释
- 选择支
- 信息堆砌

</div>

教学的第一条规则很简单：**别试图「教」**。作为教师，你的工作是提供一种体验，让学习者能够学习。教师难免有种焦虑，想把知识与理解灌输出去；但若屈服于这种冲动，靠讲述与解释来「教」，你会危及学习体验。

相反，*允许学习发生*，并相信它会。给学习者*可做之事*，让他们通过做事来学习。只有你的学生能学。遗憾的是，无论你多渴望，你都无法替学生学。你无法强迫他们学。你所能做的，只是让*他们*能够学。

### 让学生看见终点

从一开始就让学生形成他们将达成什么的想法很重要。这既有助于设定期望，也让他们在工作时看见自己正朝完成目标推进。

在教程里提供这幅图景可以很简单，例如在开头说明：*在本教程中，我们将创建并部署一个可扩展的 Web 应用。沿途我们会接触容器化工具与服务。*

这与说：*在本教程中你将学会……* **不是一回事**——后者自以为是，也是非常糟糕的模式。

### 尽早、频繁给出可见结果

你的学习者多半在做陌生又奇怪的事，尚未完全理解。理解来自把原因与结果联系起来，因此要让他们**尽快、反复**看到结果并建立联系。每一个结果都应是用户能视为有意义的东西。

学习者跟的每一步都应产生可理解的结果，无论多小。

### 维持对「应有之事」的叙述

在教程的每一步，用户都会经历一刻焦虑：这个动作会产生正确结果吗？成功教程的部分工作，是持续向学习者反馈他们**确实走在正路上**。

维持对预期的叙述：「你会注意到……」；「片刻之后，服务器会回应……」。向用户展示真实示例输出，甚至精确的预期输出。

若你事先知道**走错路**的常见迹象，不妨标出来：「若输出没有显示……，你大概是忘了……」。

为可能令人意外的动作做准备也有帮助：「该命令很可能在终端里返回数百行日志。」

### 指出学习者应注意什么

学习需要反思。反思发生在多个层次与深度，但第一层之一是学习者观察环境中的迹象。在课上，学习者通常太专注于正在做的事，除非教师**提示**，否则注意不到那些迹象。

作为教师，你的工作是在课程推进中**顺带指出**事物，从而闭合学习的回路。例如指出命令行提示符如何变化。

观察是手艺的主动部分，而非纯粹被动。它意味着留意环境——这本身就是一项技能，却常被忽视。

### 瞄准*做事的感觉*

在任何技能或手艺里，熟练者会体验到一种*做事的感觉*——目的、行动、思考与结果连成一体。

随着技能发展，它会以自信的节律流动，成为一种愉悦。就像走路的愉悦。

<div class="sidebar">

留意你自己工作中的*做事的感觉*。执行某一操作时是什么体验？

</div>

学习者的技能取决于他们发现这种感觉，并让它成为愉悦。

作为教程作者，你的挑战是让任务把目的与行动绑在一起，成为这种感觉的摇篮。

### 鼓励并允许重复

学习者会反复做能带给他们成功的练习，为了获得预期结果时的那种愉悦。这样做会再次确认他们能做到，而且管用。

重复是建立「做事的感觉」的关键；在家于那种感觉之上，是学习的基础层。

<div class="sidebar">

重复未必是最好的老师——有时它是*唯一的*老师。

</div>

在教程里，尽量让某一步及其结果可以**重复**。这在不可逆的操作中可能很难（难以回到上一步）——但尽你所能去争取。观察用户跟教程时，你常会惊讶于他们重复某一步的频率：他们只是想再确认**同样的事确实会再发生一次**。

### 无情压缩解释

*教程不是解释的地方。* 在教程里，用户专注于正确遵循你的指示并得到预期结果。*稍后*，当他们准备好时，会去找解释；此刻他们关心的是*动手*。解释会分散他们的注意力，阻碍学习。

例如，说一句*我们使用 HTTPS 因为它更安全* 往往就够了。关于 HTTPS 的长篇讨论与解释自有其位置，但**不是现在**。应提供链接或引用，让解释**可得**，却不挡路。

<div class="sidebar">

解释只在**用户**想要的那一刻才贴切。不该由文档作者来决定那一刻。

</div>

解释是教师最难抵制的诱惑之一；即便有经验的教师也难以接受「学生的学习并不依赖解释」。这很自然。我们一旦掌握某物，就依赖抽象的力量来为自己框定它——我们也想这样框定给别人。理解意味着把握一般观念，而抽象是理解的逻辑形式——但这些并不是教程里需要的，也不是成功学习或教学运作的方式。

你必须亲眼看见：当教师一番好意的解释打破学习的魔法时，学生专注的注意如何在空气中消散。

### ……并紧扣具体

在学习情境里，你的学生处在当下，而当下由**具体**事物构成。你要负责建立并维持学生的流动，从一个具体动作与结果流向下一个。

聚焦*这个*问题、*这个*动作、*这个*结果，以这种方式引导学生从一步走向另一步具体。

若一味紧扣具体与特殊，似乎剥夺了学生看见或把握更大一般模式的机会，但事实相反。我们的大脑最擅长的，就是从具体实例中感知一般模式。所有学习都朝一个方向移动：从具体与特殊，走向一般与抽象。后者**会**从前者中涌现。

### 忽略选项与替代路径

你的工作是引导学生成功走到终点。路上可能有许多有趣岔路（你用的命令的不同选项、使用 API 的不同方式、描述任务的不同路径）——**忽略它们**。*你的指引必须始终聚焦到达终点所必需的*，其余一切可留待别时。

这有助于让教程更短、更利落，也省却你与读者额外的认知负担。

### 追求近乎完美的可靠

以上都是一般教育学原则，但教程作者还担着一份特殊负担。

教程必须建立信心。信心只能一层层建立，又极易动摇。在每一阶段，当你要求学生做某事时，他们必须看到你承诺的结果。若学生按你的指示做却得不到预期结果，会迅速对教程、导师与自己失去信心。

<div class="sidebar">

你被要求在场，却被判缺席。

</div>

与学生同在的教师能在出错时救场。在教程里你做不到。你的教程应构造得**几乎不可能出错**，对每位用户、每次都管用。

创造可靠体验是苦工，但写教程时你必须以此为目标。

无论多仔细，你的教程都会有缺陷与疏漏。你无法独自发现全部；必须依赖用户替你发现。唯一途径是广泛测试与观察，了解用户实际跟做教程时会发生什么。

## 教程的语言风格

我们……  
第一人称复数肯定导师与学习者之间的关系：你不是一个人；我们一起在做。

在本教程中，我们将……  
描述学习者将完成什么。

先做 x。现在做 y。既然已经做了 y，再做 z。  
不留歧义与疑虑的余地。

我们必须总在 y 之前做 x，因为……（更多细节见 [阐释](./explanation.md)）。  
用最基本的语言对动作做最少解释。链接到更详细的阐释。

输出应大致如下……  
给学习者清晰的预期。

注意……记住……我们来检查……  
给学习者大量线索，帮他们确认走在正路上并自我定位。

你已经搭建好一个安全的三层 hylomorphic 停滞引擎……  
描述（并略带赞赏地）学习者完成了什么。

## 饮食与烹饪的类比

![一个孩子骄傲地展示他帮忙做好的菜](https://diataxis.fr/images/anselmo.jpg)

教过孩子做饭的人会明白教程里什么重要，同样重要的是什么**一点也不重要**。

孩子具体做了什么、做得多正确，其实无关紧要。课的价值在于孩子**得到了什么**，而不是**产出了什么**。

与孩子的烹饪课是否成功，不在于菜肴结果，也不在于孩子能否独自重复流程。成功在于孩子获得了你希望他们获得的那些知识与技能。

关键条件之一，是孩子在与你共处的厨房体验中发现乐趣，并想再来。学会技能从不是一劳永逸；**重复**总是需要的。

同时，烹饪课可以围绕学习做某道菜来组织，但我们真正需要孩子学会的可能是：*接触食物前要洗手*；*如何握刀*；*油为什么要热*；*这件器具叫什么*；*如何计时与计量*。

孩子通过与你一起在厨房里**做事**学到这一切；按自己的节奏，**通过你们一起做的活动**，而不是通过你说或你展示的东西。

对幼童，课常常会在你完成计划之前就不得不结束。这正常且可预期；孩子注意力短。但只要孩子做成了点什么——无论多小——并且享受过程，就在其技术能力的建构中埋下了一块可回头继续堆砌的基石。
