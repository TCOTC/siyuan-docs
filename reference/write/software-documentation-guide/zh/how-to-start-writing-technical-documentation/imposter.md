# Conquering imposter syndrome

你是技术写作者。职业生涯中，你可能听过「不过是写文档的」这类说法——可能来自更偏工程的同事，也可能来自自我怀疑。

许多团队里会出现类似叙事：谁都能写两句，但写文档的人不写代码，所以「不懂技术」；文档该工程师写，但他们没时间或不想写；真到取舍时，产品/代码永远优先于文档。于是写文档仿佛天然低人一等。

再加上非技术背景，很容易演变成冒名顶替综合征：觉得自己在「扮演」专家，随时会被拆穿。

若你担心自己在「冒充」技术人员，也许需要重新理解：这份工作真正需要的技能到底是什么。

## "Anyone can write"

人人都能写字，但把技术内容写清楚是另一回事。你被录用，不是因为你「会把首字母大写、标点放对」，也不是在简单复述工程师的话并排版。你的能力远不止于此。

你需要从大量信息中提炼意义，并用受众能消化的方式传达；把工程输入整理成易于理解的块，再组织成有意义的顺序；把这些内容放进能帮助用户解决业务问题的情境里。你传递的不只是 WHAT 与 HOW，还有 WHY。你处在工程、产品与用户赋能的交汇点。

这要求你理解认知、沟通、学习过程，以及用户面对的真实场景——这些并不会因为某人「更懂代码」就自动拥有。

## Perspective

你的读者是谁？

- 刚开始上手的新手  
- 尝试新功能的中高级用户  
- 卡在某个步骤上的各类用户  

你「不是技术极客」反而是优势：优秀技术写作者擅长代入不同视角，判断读者需要哪些信息、如何呈现。受众在学习程度、目标与背景上往往差异很大，你要判断该包含什么、包含多少。

过于「内行」有时反而会让你跳过对新手至关重要的步骤；你不会假设读者已经知道那些「显而易见」的细节。

## Complex information and user context

工程师深耕自己的领域，习惯外人听不懂。你得到的第一个回答可能很浅，因为他们还没摸清你的理解深度。

这不代表你学不会复杂技术；多轮对话很正常，而你也擅长提出正确问题、追根究底，让文档对所有用户都有价值。

你不必会写代码，甚至不必读懂源码；你需要理解软件如何工作，以及它如何帮助用户解决业务问题。

## Dealing with knowledge gaps

当然，你仍要学习所记录的技术，并愿意走出舒适区。可以注意：

- 听不懂时不要盲信；继续追问、阅读，补齐所需知识。  
- 不要只待在写得顺手的章节；优先写用户最需要的部分，即便那里你更不熟。  
- 内向也要克服「不好意思打扰别人」的心理。  
- 你的角色不是全知全能，而是把团队知识综合成对用户最有用的形态。  
- 知识缺口可能是双向的：主动与内部干系人同步你在做什么。  
- 诚实面对会与不会；不确定或出错时要坦诚说明。  
- 保持好奇心，持续提问与学习。

## Documentation as a part of the product

有些问题要在组织层面解决：赚钱的是产品而不是文档，这是事实。但用户体验与「用户能否用产品达成目标」强相关，文档在其中扮演重要角色。把「有意义的文档」写进 Definition of Done，可以从一开始就确立文档对体验的贡献。
