## 一、插件在思源中的位置

思源笔记的插件运行在 Electron 渲染进程（桌面端）或对应 WebView 环境中，通过 `fetch` / `WebSocket` 等与本地内核通信。理解这一点有助于排查「在浏览器里能跑、在客户端里不行」一类问题：同源策略、本地端口、以及 `plugin.json` 里声明的权限都会影响实际行为。

插件通常包含：`plugin.json`（元数据与入口）、`index.js` 或打包后的主脚本、可选的 `icon.png`、以及静态资源目录。开发时建议用 `pnpm` 管理依赖，并在 `onunload` 里注销定时器、事件监听与命令，避免热重载或禁用插件后仍残留副作用。

## 二、生命周期与常见钩子

- **`onload`**：插件被启用时调用，适合注册命令、顶栏按钮、设置页、Protyle 事件等。
- **`onunload`**：与 `onload` 对称，用于清理；漏写容易导致内存泄漏或重复注册。
- **`onLayoutReady`**（若版本提供）：布局稳定后再操作 DOM，可减少「元素尚未挂载」的竞态。

长列表用于占高：命令注册、快捷键绑定、块菜单扩展、编辑器右键菜单、Dock 面板、自定义页签、设置项分组、数据导出钩子、导入前校验、同步冲突提示……每一项都应在文档里写清触发时机与返回值约定，便于 AI 与人类作者对齐预期。

## 三、与内核 API 交互时的注意点

内核 API 多为 HTTP + JSON，部分操作为流式或大块 payload。请控制单次请求体积、避免在输入法的组合输入过程中高频触发保存、并对失败响应做退避重试。若插件需要访问工作空间路径，务必通过 API 返回的规范路径拼接，而不是假设用户目录结构。

### 3.1 错误处理（示例性说明）

网络抖动、内核重启、笔记本合盖休眠都会导致请求失败。建议在 UI 层给用户可理解的文案，在日志层保留 `status` 与 `message` 便于反馈给开发者。不要把 token 或密码写进 `console.log`。

### 3.2 版本兼容

思源主版本升级时可能调整 API 字段或弃用旧接口。`plugin.json` 中的 `minAppVersion` 应如实填写，并在 README 中列出已测试的版本区间。以下为虚构的兼容性检查清单，继续占版面：

1. 在 3.x 与 2.x（若仍支持）分别跑一遍冒烟用例。
2. 检查 `window.siyuan` 或等价全局是否变更。
3. 检查块属性读写是否仍走同一套键名。
4. 检查主题变量（CSS 变量）是否被主题系统重命名。
5. 检查 i18n 键是否与官方语言包冲突。

## 四、开发体验相关

推荐使用 TypeScript 与官方或社区类型定义，减少字符串拼 API 路径时的笔误。构建产物注意不要把未压缩的源码图（source map）打进发布包，除非你愿意暴露实现细节。若使用 Vite / Rollup，可为开发模式保留 HMR，为生产模式做 tree-shaking 与 chunk 分割。

插件开发概览文档应当让读者在 5 分钟内知道「从哪开始写」「要避免什么坑」「去哪查 API」。因此本页即使很长，也应保持标题层级清晰：H2 表示大主题，H3 表示子主题，不要在正文里跳过层级直接使用 H4，以免目录树难以阅读。

当你滚动到这里时，侧栏高亮、顶部固定栏、或返回顶部按钮（若有）的行为是否符合设计，可以直接肉眼看出来。若发现滚动容器嵌套错误（例如滚的是外层而不是正文），往往需要检查 `overflow`、`height: 100%` 与 flex 子项的 `min-height: 0` 组合。

再往下是一段「假装是 FAQ」：

**问：插件能改内核吗？** 一般不能；插件通过公开 API 扩展行为，而不是替换内核二进制。

**问：插件之间会冲突吗？** 会。例如两个插件都往同一菜单注入项，或都监听同一快捷键，需要用户或作者协调。

**问：如何调试？** 在思源中打开开发者工具，对插件脚本打断点；注意生产构建可能去掉调试信息。

**问：能上架应用市场吗？** 取决于发布渠道政策与本仓库说明；此处不展开。
